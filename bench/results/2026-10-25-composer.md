# Composer and parallel creates, 2026-10-25

M2 Max, macOS 27, berth on its 7.2.12 kernel with the polling driver,
OrbStack 2.2.5. The Mac was busy (load average 8-13 from other apps), so
the engines were alternated run by run, and the benchmark folders end in
`.noindex` (Spotlight indexed the 31k files of each run before).

## What changed

1. **One poller per virtqueue** in the guest driver. With every waiting CPU
   polling, the queue's lock was held by pollers most of the time.
2. **ioctls answered in the guest.** musl's `fopen()` sends `TIOCGWINSZ`
   for every file opened for writing; Composer's install made ~31k of them.
   On its own this didn't show in the timings (each was a ~6 µs round
   trip, and Composer's requests mostly come one at a time).
3. **Closes off the request path** (evicted cached files, forgotten nodes):
   the server's CREATE under Composer 69 -> 63 µs.

Tried and not kept: no host polling (`BERTH_FS_POLL_US=0`, 11.8 s), a
30 µs host poll window (same as 100).

## Where the rest goes

Server-side, per install: ~290k requests, 5.3 s of serving in a ~7.3 s run,
so nearly serial. CREATE 31k × 63 µs, SETATTR 40k × 19 µs, WRITE 33k × 22
µs, LOOKUP 69k × 8 µs, MKDIR 8.7k × 64 µs. In isolation the server's CREATE
costs 45 µs (native open+fstat 42): the rest is the Mac's cores being
shared with the VM's 12 vCPUs.
