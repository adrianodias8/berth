# berth vs OrbStack for the README: 2026-10-25

Apple M2 Max, 32 GiB, macOS 27.0.1; berth fa78d7e (kernel 7.2.12-berth,
polling driver), OrbStack 2.2.5, DDEV 1.25.2, Drupal CMS (38,965 files).
Each engine alone, the other stopped. `bench/compare.sh` (in
`2026-10-25-1741.md`), then `bench/workloads.sh` and `bench/ddev-drupal.sh`
on each engine, then two more DDEV runs per engine, alternating engines.

container -> Mac was 18–28 Gbit/s on berth in earlier runs
(`2026-10-24-workloads.md`); this direction varies from run to run.

## Later: docker build on the classic image store

`docker build -q --no-cache` of `workloads.sh`'s build (5,000-file context,
`apk add python3`, COPY), four runs each after a warm-up, berth before and
after OrbStack:

| | runs |
|---|---|
| berth, containerd image store (before) | 3.90–4.06 s |
| berth, classic overlay2 store (`image_store` default) | 2.16–2.46 s, 2.20–2.78 s |
| OrbStack 2.2.5 (overlay2 on btrfs, Docker 29.8.2) | 2.65–3.24 s |

BuildKit's step times showed the gap was the image export: `exporting
layers` 1.0 s and `unpacking` 0.4 s on containerd's store, against 0.2 s;
the context upload took 0.3 s (0.1 s cached) on berth and 0.5 s on
OrbStack. `apk add` (the internet) varies 1.5–1.8 s on both.
